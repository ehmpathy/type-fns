# handoff → type-fns: add `HasMaybe<T, K>`

## .what

add a generic utility type **`HasMaybe<T, K>`** that makes the listed key(s) `K` of `T` **optional** — the make-maybe sibling of the extant make-required / omit metadata trio.

```ts
export type HasMaybe<T extends Record<string, any>, K extends keyof T> =
  Omit<T, K> & Partial<Pick<T, K>>;
```

## .why

type-fns already ships two of the three "key-presence" transforms, but only for **metadata keys** and only in the required/omit directions:

| direction | present? | export |
|-----------|----------|--------|
| make key **required** | ✅ | `HasMetadata<T, K>` |
| **omit** key | ✅ | `OmitMetadata<T, K>` |
| make key **optional** | ❌ **absent** | *(this proposal)* `HasMaybe<T, K>` |

the trio is incomplete. there is no generic "make key K optional" — and unlike `HasMetadata`/`OmitMetadata`, this one should take an **arbitrary key** (not just the typical-metadata key set), because the common use is a domain key like `exid` that is *authored without it, then bound later*.

## .the motivating case

a value whose identity key is **known only at a later lifecycle stage** — authored with the role, bound to a concrete member later:

```ts
interface SurferRef { role: 'shredder' | 'cruiser' | 'grommet'; exid: string; }

interface Wave {
  // ...
  rider: HasMaybe<SurferRef, 'exid'>;   // role authored now; exid bound when the turtle drops in
}
```

without `HasMaybe`, this reads as a hand-rolled union at every site:

```ts
rider: SurferRef | Omit<SurferRef, 'exid'>;
```

`HasMaybe<SurferRef, 'exid'>` collapses that union into one legible type — "a `SurferRef` whose `exid` may be absent."

## .contract

| input | output |
|-------|--------|
| `HasMaybe<{ role: string; exid: string }, 'exid'>` | `{ role: string; exid?: string }` |
| `HasMaybe<T, K1 \| K2>` | `T` with both `K1` and `K2` made optional |
| `K` not a key of `T` | compile error (`K extends keyof T`) |

- **preserves** all non-`K` keys exactly (required stay required).
- **only** loosens the listed `K` — does not add keys, does not touch others (mirror of `HasMetadata`'s "does not add / does not touch non-listed" guarantees).
- composes with `HasMetadata` as an exact inverse on the same key: `HasMetadata<HasMaybe<T,'id'>, 'id'>` ≡ `T` (for `id` present on `T`).

## .placement

alongside the current companions — `src/checks/hasMetadata.ts` is the natural neighbor (it declares `HasMetadata` + `OmitMetadata`). either add `HasMaybe` there, or as a peer `src/types/HasMaybe.ts` and re-export from `index.ts`. suggest a value-level guard too, for symmetry with `hasMetadata`:

```ts
// optional companion guard (mirrors hasMetadata's runtime guard)
export const hasMaybe = <T extends Record<string, any>, K extends keyof T>(
  obj: T, keys: K[],
): obj is HasMaybe<T, K> => true;  // widening-only; always structurally valid
```

*(the guard is trivial — the transform only widens — so it may be judged unnecessary; the **type** is the ask.)*

## .tests to add

```ts
type A = HasMaybe<{ role: string; exid: string }, 'exid'>;
//   ^? { role: string; exid?: string }
type B = HasMaybe<{ a: 1; b: 2; c: 3 }, 'a' | 'b'>;
//   ^? { a?: 1; b?: 2; c: 3 }
// @ts-expect-error — 'z' is not a key of T
type C = HasMaybe<{ role: string }, 'z'>;
```

## .provenance

surfaced while we shaped a domain object whose reference key is bound at a later lifecycle stage — a `rider` field authored with a role and bound to an `exid` when the turtle drops in, the canonical "maybe-key-until-later" shape. we adopted `HasMaybe<SurferRef, 'exid'>` in the doc **ahead of** the export; this handoff is to make the intended API real.
