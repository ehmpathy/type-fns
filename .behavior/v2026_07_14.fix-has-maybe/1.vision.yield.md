# 1.vision — `HasMaybe<T, K>`

## the outcome world

### day-in-the-life

a domain author models a value whose identity key is bound *later* in its lifecycle. today they hand-roll a union at every site:

```ts
rider: SurferRef | Omit<SurferRef, 'exid'>;
```

after this wish, they write one legible type:

```ts
rider: HasMaybe<SurferRef, 'exid'>;   // role authored now; exid bound when the turtle drops in
```

### before/after contrast

| | before | after |
|---|--------|-------|
| make key **required** | `HasMetadata<T, K>` ✅ | unchanged ✅ |
| **omit** key | `OmitMetadata<T, K>` ✅ | unchanged ✅ |
| make key **optional** | hand-rolled union ❌ | `HasMaybe<T, K>` ✅ |

the trio becomes complete: require / omit / maybe.

### the "aha" moment

`HasMaybe<SurferRef, 'exid'>` reads aloud as *"a SurferRef whose exid may be absent."* the union collapses into a single named intent, and it composes as an exact inverse of `HasMetadata` on the same key:

```ts
HasMetadata<HasMaybe<T, 'id'>, 'id'>  ≡  T   // for id present on T
```

## user experience

### usecases & goals

- **author-now, bind-later** — model a key known only at a later lifecycle stage (the canonical `exid`-bound-later shape).
- **legibility** — replace repeated `T | Omit<T, K>` unions with one named type.
- **symmetry** — round out the require/omit/maybe trio already half-shipped by type-fns.

### contract inputs & outputs

```ts
export type HasMaybe<T extends Record<string, any>, K extends keyof T> =
  Omit<T, K> & Partial<Pick<T, K>>;
```

| input | output |
|-------|--------|
| `HasMaybe<{ role: string; exid: string }, 'exid'>` | `{ role: string; exid?: string }` |
| `HasMaybe<{ a: 1; b: 2; c: 3 }, 'a' \| 'b'>` | `{ a?: 1; b?: 2; c: 3 }` |
| `HasMaybe<T, 'z'>` where `'z'` ∉ `keyof T` | compile error (`K extends keyof T`) |

guarantees (mirror of `HasMetadata`):
- **preserves** all non-`K` keys exactly — required stay required.
- **only** loosens the listed `K` — does not add keys, does not touch others.

### what it looks like to leverage

```ts
import type { HasMaybe } from 'type-fns';

interface SurferRef { role: 'shredder' | 'cruiser' | 'grommet'; exid: string; }

interface Wave {
  rider: HasMaybe<SurferRef, 'exid'>;
}

// authored now — exid absent, allowed
const draft: Wave = { rider: { role: 'cruiser' } };

// bound when the turtle drops in — exid present, allowed
const active: Wave = { rider: { role: 'cruiser', exid: 'turtle_123' } };
```

### timeline

author authors `rider` with just a `role` → the turtle drops in on the wave → `exid` is bound. the type accepts both the pre-bind and post-bind shapes without a union at the call site.

## mental model

- **how they'd describe it to a friend**: "it's `Partial`, but scoped to only the keys you name — the rest stay required."
- **analogy**: `HasMaybe` is to `Partial` what `Pick` is to a full type — a targeted, key-scoped version.
- **their terms vs ours**: users say "make exid optional / maybe-there"; we say "make key `K` optional — the make-maybe sibling of the make-required (`HasMetadata`) / omit (`OmitMetadata`) trio."

## evaluation

### how well it solves the goals

directly. the type is a one-line composition of stdlib `Omit` + `Partial` + `Pick`, so it is zero-risk and immediately legible. it completes the trio and matches the wish's motivating case exactly.

### pros

- tiny, pure type — no runtime cost, no dependencies.
- `K extends keyof T` keeps callers in a pit of success (typos on `K` fail to compile).
- multi-key support falls out for free (`K1 | K2`).
- composes cleanly with the extant `HasMetadata`/`OmitMetadata`.

### cons / tradeoffs

- **naming asymmetry**: `HasMetadata`/`OmitMetadata` default `K` to the typical-metadata key set; `HasMaybe` requires an explicit `K` (no default). this is intentional per the wish — the common use is an arbitrary domain key like `exid`, not a metadata key — but it means the three siblings do not share an identical signature shape. worth calling out so reviewers don't expect a `MetadataKeys` default.
- **name family**: `HasMaybe` reads as a member of the `Has*` family (like `HasMetadata`) rather than the `*Metadata` family. that is the right call since it is not metadata-scoped, but the name choice is a decision to confirm (see open questions).

### edgecases & pit-of-success

| edgecase | behavior |
|----------|----------|
| `K` not a key of `T` | compile error via `K extends keyof T` |
| `K` already optional on `T` | no-op — stays optional (widening only) |
| `K = keyof T` (all keys) | equivalent to `Partial<T>` |
| union `K1 \| K2` | both made optional, others untouched |

## open questions & assumptions

### assumptions
- **placement**: add `HasMaybe` as a peer type. the wish suggests either colocating in `src/checks/hasMetadata.ts` or a peer `src/types/HasMaybe.ts` re-exported from `index.ts`. leaning toward a peer file `src/types/HasMaybe.ts` for single-responsibility (mirrors the other `src/types/*` entries like `PickOne`, `PickAny`), but colocating with the metadata trio is also defensible for discoverability.
- **guard**: the wish flags the `hasMaybe` value-level guard as *trivial / possibly unnecessary* (it only ever returns `true` since widening is always structurally valid). assumption: **skip the guard** unless the wisher wants strict symmetry with `hasMetadata`. the type is the ask.
- **signature**: use the wish's exact `Omit<T, K> & Partial<Pick<T, K>>` form rather than `HasMetadata`'s `T & Required<Pick<...>>` style, since we're loosening not tightening.

### open questions (triaged)

1. **file placement** — **[answered]** peer `src/types/HasMaybe.ts`. resolved by extant convention: pure types live in `src/types/*` (`PickOne`, `PickAny`, `Empty`), guards in `src/checks/*`. `HasMaybe` is a pure type, so it belongs in `src/types/`, re-exported from `index.ts`. (wisher may still colocate with the metadata trio for discoverability, but the code convention answers it.)
2. **guard** — **[answered]** omit the `hasMaybe` runtime guard. resolved by logic: a widen-only transform is always structurally valid, so the guard can only ever return `true` — it adds export surface without verification value. reversible if the wisher later wants strict export-surface symmetry with `hasMetadata`.
3. **name** — **[answered]** `HasMaybe`. the wisher already chose this name in the wish's title and contract; no open decision. alternatives (`PartialPick`, `OptionalKeys`, `MaybeKeys`) noted only for the record.

### must-validate in execution ⚠️
- **`interface` vs `Record<string, any>` constraint**: the wish's real-world case uses `interface SurferRef`, but an `interface` does not carry an implicit index signature and may fail the `T extends Record<string, any>` bound (a known TS gotcha). the extant `HasMetadata` tests only cover `type` aliases (`type FlowerPot = {...}`), so the interface case is unproven. the test suite **must** include an `interface`-typed case; if it fails the bound, loosen the constraint (e.g. `object`, `Record<PropertyKey, any>`, or drop it and rely on `keyof T`).
- **assert structurally, not by hover string**: `Omit<T, K> & Partial<Pick<T, K>>` may render as the literal intersection rather than a flattened `{ role: string; exid?: string }`. tests should assert assignability both directions (as `hasMetadata.test.ts` does), not string-match the `^?` hover.

### research needed
- none external — pure TypeScript stdlib composition (`Omit`, `Partial`, `Pick`).

## groundwork

### external research
none — no external dependencies. `HasMaybe` composes only TypeScript built-in utility types.

### internal research

confirmed against the current repo (`ehmpathy/type-fns`, worktree `fix-has-maybe`):

- **not yet implemented**: `HasMaybe`/`hasMaybe` appear only in `.behavior/v2026_07_14.fix-has-maybe/0.wish.md` — no source definition exists.
- **sibling contracts** (`src/checks/hasMetadata.ts:36-69`): `HasMetadata<T, MetadataKeys = TypicalMetadataKeys>` and `OmitMetadata<T, MetadataKeys = TypicalMetadataKeys>` — both default `K` to the typical-metadata set. `HasMaybe` intentionally diverges by requiring explicit `K` (per wish).
- **runtime guard pattern** (`src/checks/hasMetadata.ts:85-93`): `hasMetadata` is a type-guard `obj is HasMetadata<...>` checking `keys.every(k => obj[k] !== undefined)`. a `hasMaybe` guard would trivially return `true` (widening only).
- **export pattern** (`src/index.ts:1-22`): flat `export * from './...'` per module; types live under `src/types/*` (e.g. `PickOne`, `PickAny`, `Empty`) and checks under `src/checks/*`. a peer `src/types/HasMaybe.ts` would add `export * from './types/HasMaybe';`.
- **test pattern** (`src/checks/hasMetadata.test.ts`): jest `describe`/`it` with type-level assignment assertions and `@ts-expect-error` for negative cases. mirror this for `HasMaybe` (`A`, `B` positive; `C` negative per wish's `.tests to add`).
- **domain vocab to reuse**: `Has*` naming (`HasMetadata`, `hasId`, `hasUuid`), `Record<string, any>` generic constraint, `K extends keyof T` bound.

## what is awkward?

- **the default-`K` asymmetry** (noted in cons): the metadata trio defaults `K`; `HasMaybe` cannot, because its point is arbitrary domain keys. the three don't line up as a perfectly uniform family — a mild conceptual snag but the right tradeoff.
- **the guard with no effect**: a `hasMaybe` runtime guard would always return `true`, which is honest (widening is always valid) but feels hollow next to `hasMetadata`'s real presence-check. leaning to omit it to avoid a guard that can never fail.
- **name overlap risk**: `Maybe` is an overloaded term (Haskell `Maybe`, nullable-monad connotations). here it means "key may be absent," not "value may be null." the name is legible in context but carries a faint ambiguity worth a wisher confirm.
