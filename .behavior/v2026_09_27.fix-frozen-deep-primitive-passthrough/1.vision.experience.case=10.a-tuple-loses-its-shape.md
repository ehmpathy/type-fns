# case 10 — a tuple goes in, a string array comes out

> cells **A41** `[t0]` · **A43** `[t1]` · **A44** `[t2]` · `tuple × read/assign-back × top/nested` ·
> feel **sharp** · care **alterpath** · 🔴 **F9's evidence** — the **before** half of F9's clamp

## .why this case exists

the `tuple` row diverges from `array` on exactly two cells, both here. this is the one demo whose
subject is a defect in the type **#48 proposes**, not a defect it fixes. it puts F9's behavior in
front of the wisher.

## .the narrative

nef declares a lambda payload with a date range. a range has two ends, so she says so:

```ts
type DateRange = [since: string, until: string];

interface Payload {
  range: DateRange;
}
```

that is why tuples exist: arity is part of the contract, and labels make `range[0]` legible.

she wraps the payload in #48's `FrozenDeep` and forwards it. `tsc` refuses:

```
Type 'readonly string[]' is not assignable to type 'readonly [since: string, until: string]'.
  Target requires 2 element(s) but source may have fewer.
```

her tuple came back a `readonly string[]`. **length, labels, and positions are gone.** `since` and
`until` collapse into one anonymous `string` slot, repeated an unknown number of times.

### the first symptom arrives quietly

before that error, she reads an end of the range:

```ts
const since: string = frozen.range[0];
//    ^^^^^  Type 'string | undefined' is not assignable to type 'string'.
```

⚠️ **this is the degrade, and it does not look like one.** `noUncheckedIndexedAccess` widens an
index read on an *array* to `T | undefined`, never on a *tuple* — a tuple's slot 0 is known to
exist. the `| undefined` appears **because** the tuple became an array. nef reads it as a lint
annoyance, adds a `!`, and the real loss goes unnoticed — until the assign-back, or until a third
element reaches the range at runtime and no type complains.

### the aha

> **#48's array arm has the same defect the primitive arm had**: it captures a value *assignable to*
> a general shape and returns the general shape, which drops what made the specific type specific.

- primitive arm: `string & OfGlossary<G>` satisfies `T extends object`, so a branded string maps
  into a record and loses its brand.
- array arm: `[a, b]` satisfies `T extends ReadonlyArray<infer TItem>`, so a tuple is rebuilt as
  `ReadonlyArray<a | b>` and loses its arity.

⇒ **same mechanism, one arm apart.** an arm whose `infer` is wider than its input returns the wider
type — the whole wish, restated, and #48's type does it twice.

## .the bdd sketch — #48's type as written

```gherkin
given a payload with a labelled tuple, typed FrozenDeep

  [t0] when the author READS an element by index
       then the type is `string | undefined`, not `string`
        and the widened read IS the degrade, not noUncheckedIndexedAccess alone
        (a tuple's slot 0 is known to exist; an array's is not)

  [t1] when the author assigns it back to the tuple type
       then tsc refuses
        and the message says the target requires 2 elements
        and the source may have fewer                    # arity gone

  [t2] when the tuple sits one container deep
       then the refusal propagates to the whole object   # the degrade is not top-only

  [t3] when the array arm is REMOVED from the type
       then [t1] and [t2] compile                        # the clamp that proves the cause
        and every plain-array assertion still holds      # no regression on case 4/5
```

```ts
type DateRange = [since: string, until: string];

declare const frozenRange: FrozenDeep<DateRange>;

// [t0] — the quiet symptom. NOT an error; a widened read
const since: string | undefined = frozenRange[0];

// [t1] — 🔴 the arity is gone
// @ts-expect-error - Target requires 2 element(s) but source may have fewer
const backToTuple: readonly [since: string, until: string] = frozenRange;

// [t2] — and it propagates through a container
declare const frozenPayload: FrozenDeep<{ range: DateRange }>;
// @ts-expect-error - the degrade reaches the whole object
const backToPayload: { readonly range: readonly [since: string, until: string] } = frozenPayload;
```

🔴 **`[t3]` makes the case actionable.** it mirrors the wish's primitive-arm revert, pointed at the
array arm, in the opposite direction: removal makes the assertions **pass**, because removal is the
fix. measured: with the array arm cut, `[since: string, until: string]` round-trips intact, and
every array assertion in cases 4 and 5 holds (`appendix/groundwork.probe.tuple-arm.md`).

## 🔴 .the shipped type — F9's verdict

the wisher ruled (2026-09-28): **keep tuples as tuples.** the shipped type preserves a tuple as a
readonly tuple — arity, labels, positions kept — and every plain array still becomes
`readonly T[]`:

| | #48 as written | shipped |
|---|----------------|---------|
| `FrozenDeep<[since: string, until: string]>` | `readonly string[]` | `readonly [since: string, until: string]` |
| `frozenRange[0]` | `string \| undefined` | `string` |
| assign back to the tuple, top or nested | ⛔ refused | ✅ compiles |
| `number[]`, `.push`, deep-freeze of items | unchanged | unchanged |

⇒ `[t0]`–`[t2]` become the clamp's **before**: execution asserts `[t0]` as `string`, `[t1]` and
`[t2]` as plain compiles, and proves the clamp bites — red against #48's array arm, green against
the shipped one.

## .fail-safe and care

under #48 the edge does not fail safe: the message blames the author's declaration, and no
author-side edit restores the arity short of a retreat to `{ since; until }`. the verdict removes
the sharp edge from the shipped type, so no fail-safe is owed.

care stays **alterpath**: a lambda payload is `JSON.parse` output, a named pair crosses a wire as an
object far more often than a positional tuple, and the object fallback round-trips intact
(A53/A54). case 5, by contrast, is critipath — every payload with any array meets it.
