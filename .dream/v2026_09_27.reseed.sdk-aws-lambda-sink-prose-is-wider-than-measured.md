## .the gap, precisely

`src/domain.operations/genLambdaEndpoint/setEventFrozen.ts:66-69` says:

> `FrozenDeep<TInput>` makes `event` unassignable to every mutable parameter a handler forwards
> it to, so a handler must declare its sinks readonly.

and fulcrum F21 of `v2026_09_20.feat-invoke-headers-event-payload` restates it:

> `invoke: async ({ event }) => await fulfilOrder(event)   // ⛔ FrozenDeep<Order> is not an Order`

measured under typescript 5.4.5 / `@tsconfig/strictest`
(type-fns `appendix/groundwork.probe.readonly-variance.md`):

| the case | result |
|----------|--------|
| `FrozenDeep<{ y: number }>` → a `{ y: number }` sink | ✅ **compiles** |
| `FrozenDeep<{ x: { y: number } }>` → a `{ x: { y: number } }` sink | ✅ **compiles** |
| `FrozenDeep<Order>` → an `Order` sink (`Order` = a branded object) | ✅ **compiles** |
| `FrozenDeep<Wave>` → a `Wave` sink (`Wave` = a class) | ✅ **compiles** |
| `FrozenDeep<number[]>` → a `number[]` sink | ⛔ refused |
| `FrozenDeep<{ xs: number[] }>` → a `{ xs: number[] }` sink | ⛔ refused |

⇒ typescript does **not** compare `readonly` property modifiers in structural assignability — a
deliberate, long-lived unsoundness in its assignability rules. only `ReadonlyArray` refuses,
because its readonly-ness is part of the type's identity rather than a modifier on it.

## .why the prose is not simply wrong

**every envelope the sdk freezes contains an array.** `records: FrozenDeep<TShapes['record'][]>`
is a declared slot of `InvokeInputSuperset`, and one nested readonly array is enough to refuse the
whole object. so the refusal really is observed on the sdk's own shapes.

⇒ the sentence generalizes a true observation into a claim about the type. accurate where it was
written; untrue as stated.

## .the shape of the fix

qualify the two passages, in place:

> `FrozenDeep<TInput>` refuses a **write** at every depth. it also makes `event` unassignable to a
> mutable parameter **wherever an array is in the shape** — which is every envelope this sdk
> freezes, since `records` is an array and one nested readonly array refuses the whole object. on
> an array-free shape, a `readonly` property does **not** refuse a mutable sink — typescript does
> not compare `readonly` property modifiers in structural assignability.

and add a clamp beside the extant ones in `setEventFrozen.test.ts`: assert that an envelope which
holds an array refuses a mutable sink **and** that an array-free object does not. the second
assertion is the one that keeps the prose honest.

⚠️ check F21's `fulfilOrder(event)` example while there. if `Order` is array-free, the `⛔` in
that fulcrum is wrong and the conclusion it supports may need a re-read.

🔴 **and edit `rule.require.frozen-invoke-inputs.md:64` first.** it is a blocker-grade rule brief,
so it is booted into every agent's context in that repo — a false premise there is read far more
often than a jsdoc, and it is cited as authority. the same qualifier applies verbatim.
