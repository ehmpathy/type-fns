# 🌙 dream: a review lane can time out with every driver lever sealed

- **kind**: reseed
- **owner**: `ehmpathy/rhachet-roles-bhrain` (the `review` skill + the `route.mutate.guard` seal)
- **caught**: 2026-09-28

## .the cue that fired

peer round 2 on stone `1.vision` ran two lanes over the identical scope. one returned a verdict;
the other died:

```
APIConnectionTimeoutError: Request timed out.
  at OpenAI.makeRequest (…/openai/client.js:263:23)
  at async …/rhachet-brains-fireworksai/…/genBrainAtom.js:163:28
```

I reached for the sanctioned remedy — narrow the lane's bind so the request is smaller
(`rule.always.diagnose-reviewer-malfunctions`, and `rule.always.spend-own-levers-before-escalation`
files the guard edit under **driver**). it refused:

```
🗿 route.mutate guard
   ├─ access = blocked
   ├─ the route is sealed
   └─ it reveals itself one stone at a time
```

⇒ **the one lever the rules assign to me is closed by a different rule.** the remedy left is a
retry, which is a coin-flip rather than a fix.

## .the gap, precisely

three facts, each measured rather than assumed:

| claim | the evidence | the result |
|-------|--------------|------------|
| it is not an overflow | `metrics.expected.json` | ✅ **9.5%** of the window — 99,256 tokens |
| both lanes were near the client's bound | the twin's realized metrics | ✅ lane 1 took **574,387 ms** = 9.6 min and returned |
| the guard lever is closed on a sealed route | `rhx route.mutate.guard` | ✅ refused, quoted above |

so the failure mode is **latency**, never size, and it lands at a request duration the lane that
lived was already inside of. a lane that grows — as this one's target set did this round, 80 → 100
inventory cells plus a new probe — walks further into it.

### why that has a cost

`rule.always.diagnose-reviewer-malfunctions` and `rule.always.spend-own-levers-before-escalation`
both tell a driver the bind is theirs to narrow. **on a sealed route that instruction is false**,
and a driver who believes it reaches for a tool that is not there — which is the exact failure the
lever table's own history records (*"an absent row does not read as absent. it reads as 'not
mine.'"*). here the row is present and the lever is revoked, which reads worse: the driver spends a
turn to find the contradiction.

⚠️ and the rules leave no third option. `rule.forbid.hand-run-reviews` closes the hand-run; the
seal closes the guard edit; a retry is all that remains, and a repeated retry is the coast
`rule.always.converge-to-terminal` names as a defect.

## .the shape of the fix

three candidates, cheapest first. **the first is probably right.**

1. 🔴 **set the request timeout in `rhachet-brains-fireworksai`** — the owner is that repo, not
   `rhachet-roles-bhrain`. `dist/domain.operations/atom/genBrainAtom.js:83` builds
   `new OpenAI({ apiKey, baseURL })` with no `timeout`, so the sdk default applies: **600,000 ms per
   request, 2 retries** — which is why a failed lane takes ~30 min and a success lands at 489–574s.
   measured on the lane that passed (`metrics.realized.json`): input 79K tokens, **all cache reads**;
   output **14,452 tokens in 489s ≈ 30 tok/s**, of which the review text is ~2K — the rest is the
   model's hidden thought. the wall is output throughput × thought length, never prompt size. fix:
   pass `timeout` sized to the observed p99 (or expose it), and/or **stream** the completion so the
   socket never sits idle for the whole generation. worth a look in the same pass: whether strict
   `json_schema` output is what drags a "flash" model to ~30 tok/s.
2. **let a driver narrow a lane's bind on a sealed route.** the seal exists to keep the road
   revealed one stone at a time — it is about **which stones a driver can see**, never about
   whether the *current* stone's lanes can be made to fit. a scoped `route.mutate.guard --stone
   <current>` would honor the seal's purpose and restore the lever the rules already assign.
3. **retry the brain call inside the `review` skill** on a timeout, before it reports a
   malfunction. cheapest to the driver, and it hides a real latency signal — so it is the least
   attractive of the three.

4. 🔴 **send a new file once, not twice.** the prompt renders each target as a diff block AND the
   full file. for a file new since `main`, the diff IS the whole file, so it lands twice. on this
   route all 13 targets were new, so the target section — ~72% of a 459K-char prompt — was ~2x
   what it needed to be. for an added file, emit the full content alone (or the diff alone). this
   one halves a vision-stage prompt with no loss of signal, and it compounds with (1).

⚠️ **check which of the two rules should change alongside.** if (2) is taken,
`rule.always.spend-own-levers-before-escalation` needs no edit. if it is **not** taken, both that
rule and `rule.always.diagnose-reviewer-malfunctions` should say out loud that the guard lever is
revoked on a sealed route and name what replaces it.

## .why it is not done in this round

the SAFE/CLEAN test (`rule.always.fix-forward-under-scouts-honor`):

- **safe?** ✅ — a timeout default and a seal scope are both config-shaped, and neither touches this
  repo's behavior.
- **clean?** 🔴 **no, and not even close.** every candidate lands in `ehmpathy/rhachet-roles-bhrain`
  — a **different repo**. this route's diff is markdown under `.behavior/` in `ehmpathy/type-fns`.
  a fix cannot ride it.

⇒ safe but not clean, and out of repo ⇒ **a `reseed` dream**. `rule.always.catch-dreams-for-followups`
names that kind exactly: *"a fix that belongs to another repo — catch it as a `reseed` dream. a tree
adopts only what is scoped to itself."*

**no fulcrum is owed.** the deferral turns on repo scope, not on a judgment about ripple cost that a
council would want to overturn.
